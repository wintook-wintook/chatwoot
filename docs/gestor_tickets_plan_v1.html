🎯 Visión general

El Gestor de Tickets es un módulo nuevo que separa claramente tres conceptos que hoy están mezclados en Wintook. El objetivo es establecer una distinción formal entre el canal de comunicación, el problema del cliente, y las acciones automáticas que operan sobre ese problema.

Regla de oro: Un cliente puede tener 1 conversación activa · múltiples tickets · múltiples seguimientos por ticket.

Conversación

Canal de comunicación (WhatsApp, web, email). Modelo Conversation existente — sin cambios.

CaseTicket NUEVO

El problema o necesidad concreta del cliente. Tiene tipo, prioridad, estado y SLA propios.

ContactTracking

Acción automática sobre el ticket — la secuencia de seguimiento programada. No es el ticket.

CaseEvent NUEVO

Historial auditable e inmutable de todo lo que ocurre en un ticket.

CaseRule NUEVO

Reglas configurables por cuenta que automatizan asignaciones, escalados y cambios de estado en cascada.

Cuándo se dispara: Cuando KnowledgeBaseResponseService no pudo resolver la consulta, el job verifica si existe @crear_ticket en el complementary_prompt y delega a Cases::TicketCreatorService.

🔗 Integración con el bot — hook

Diagrama de secuencia — hook en ContactTrackingResponseAnalyzerJob
sequenceDiagram participant Job as ContactTracking\nResponseAnalyzerJob participant Orch as Cases::\nOrchestratorService participant Engine as Cases::\nRuleEngineService participant DB as CaseEvent Note over Job: process_message_for_tracking() Job->>Orch: find_active_ticket(account, contact, conversation) alt Ticket encontrado Orch-->>Job: ticket Job->>DB: create(event_type: message_received, origin: bot) Job->>Engine: evaluate!(ticket, trigger_message) Engine-->>Job: acciones ejecutadas else Sin ticket activo Orch-->>Job: nil end Note over Job: continúa flujo existente sin cambios rect rgb(240, 253, 244) Note over Job,DB: Todo este bloque está envuelto en rescue —\nun fallo nunca rompe el bot end 
# [Gestor de Tickets] hook — falla silenciosamente para no romper el bot
begin
  ticket = Cases::OrchestratorService.new(
    account:      message.account,
    contact:      message.conversation.contact,
    conversation: message.conversation
  ).find_active_ticket

  if ticket
    ticket.update_columns(first_response_at: Time.current) if ticket.first_response_at.nil?
    ticket.case_events.create!(
      account:    message.account,
      event_type: :message_received,
      origin:     :bot,
      payload:    { message_id: message.id }
    )
    Cases::RuleEngineService.new(ticket, trigger_message: message).evaluate!
  end
rescue => e
  Rails.logger.error("[GestorTickets] hook error: #{e.message}")
end

📝 Notas importantes

Convención: Tablas, columnas y enums siempre en inglés — igual que Chatwoot. Las etiquetas de UI se muestran en español.
ContactTracking ≠ CaseTicket: El ContactTracking es una acción automatizada sobre el ticket, no el ticket mismo. Un ticket puede tener múltiples ContactTrackings asociados.
Seguridad del hook: Todo el código del Gestor de Tickets va en rescue. Un fallo nunca rompe el flujo de atención existente.
ConceptoEs el contenedor de
ConversationMensajes (el canal de comunicación)
CaseTicketEl problema o necesidad concreta del cliente
ContactTrackingAcciones automáticas programadas sobre el ticket
CaseEventHistorial inmutable de todo lo ocurrido
CaseRuleAutomatización configurable por cuenta
  • CaseRuleEngine evalúa en cascada por position. Si continue_on_match: false, para en el primer match.
  • Auto-cierre: 72h después de status resolved sin actividad → closed.
  • @crear_ticket no tiene parámetros — exclusivo de Wintook, sin integración a sistemas externos.
  • Los CaseEvent son solo de inserción — nunca se editan ni eliminan.
